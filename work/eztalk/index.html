01

The problem

Recognition is one step.
Expression is the goal.

A person may still need to repeat an utterance, repair a transcription, or assemble a complete response. These steps add effort when speaking or operating a phone is difficult.

ezTalk is designed to reduce that effort through different levels of assistance. The user stays involved in choosing what to say.

Context-aware communication

ezTalk combines relevant personas, scenarios, conversation history, and keywords according to the communication workflow and user-selected context. The composition can vary between expressing an idea and preparing a reply. Suggested wording remains editable, and the user chooses the final message.

03

Engineering decisions

Constraints, choices & tradeoffs

Three choices that
shape the experience.

A

Offer assistance without taking over the message.

A fluent sentence may not reflect the intended meaning. The interaction offers candidate expressions that users can select or edit, while retaining a less assisted recognition path.

Tradeoff

A deliberate review step adds an action, but gives the user a way to reject generated wording.

B

Split speech processing and semantic assistance.

On-device target speaker extraction, voice activity detection, and recognition are used where the mode needs them. Cloud-based Gemini supports expression completion and reply suggestions.

Tradeoff

Local inference uses mobile resources; cloud assistance depends on connectivity and the text or context sent for processing. Not every mode works fully offline.

C

Make conversation roles explicit.

Reply distinguishes listening to a partner from expressing the user's own message. An explicit role switch provides a visible listening state before adding automatic speaker diarization.

Tradeoff

Manual switching adds an action. It keeps the role controllable and reuses the recording interaction without another automatic classification step.

04

Privacy & security

Personal expression.
Thoughtful data boundaries.

Privacy shapes where speech is processed and how supported data is synchronized. Speech processing runs locally where appropriate; Gemini text/context requests cross a separate cloud boundary.

Supported sync encrypts locally before Firestore storage. Passkey-protected key recovery lets another device decrypt downloaded records locally, provided an available passkey can be used. This protection does not cover all local files or cloud AI requests. Recovery after losing all available passkeys is not yet implemented.

On-device ML delivery

On Android, I integrate streaming audio and native inference into communication workflows, including personalized ASR. ASR/TSE update availability uses client/server SHA-256 comparisons, and users can update or skip. Model delivery must account for runtime assets, native-library compatibility, and recording lifecycle. Content-hash comparison identifies model changes; it does not establish signed authenticity.

I independently migrated the open-source Project VOICE from web to Android, integrated enhancements, and received testing feedback. This contribution is specific to the Android migration, not ownership of the upstream project. View my Traditional Chinese contribution branch.

Human-Led, AI-Assisted Engineering

I define the problem, desired outcome, and constraints. I use AI coding tools to explore alternatives, discuss trade-offs, and support implementation, then make the architectural and implementation decisions myself. The workflow varies by task; I remain responsible for the result and its maintainability.

I set expectations for test-first development, regression checks, and branch walkthrough documentation. Tests make intended behavior reviewable; walkthroughs record what changed, why, the affected components, validation results, and unresolved issues. These are engineering expectations, not a claim that every change followed strict TDD.

Current limits & evaluation

  • Target-speaker extraction can still admit loud, continuous background speech.
  • Cloud-assisted expression depends on network availability, and generated wording can misinterpret intent.
  • The modes run on real Android hardware, as reported during development. Everyday usability, semantic fidelity, communication benefit, and device performance require further evaluation. The security design still needs formal review.
